# Heidelberg 2013 — Gold Recovery

[View the model page](https://2013.igem.org/Team%3AHeidelberg/Modelling/Gold_Recovery)

## Note

- Use one practical question to frame the write-up.
- Show the complete process before explaining its parts.
- End by returning to the opening question with a clear judgment and honest
  limitations.
- Do not follow its introduction; ours will introduce our own problem and
  system differently.

# Peking 2025 — Model

[View the model page](https://2025.igem.wiki/peking/model/)

## Note

- Introduce the problem, the proposed system, why modelling was needed, and the
  journey the reader will follow.
- Let the sections follow the physical journey of the subject through the
  process.
- Use a side content menu to keep a long model write-up navigable.
- Give each model a consistent internal flow: why the stage matters, question,
  assumptions, model, finding, validation, effect on the project, and handover
  to the next model.
- Keep the connection between models visible by stating what each model passes
  to the next.

## Use of graphs

- Place each graph beside the claim or result it supports.
- Visualize how the important quantity changes over time instead of giving only
  a final value.
- Compare operating conditions when the comparison informs a design decision.
- Use spatial views when movement or transfer through the system matters.
- Show how influential parameters change the outcome.
- Put experimental, literature or control-based validation beside the model
  result it validates.
- Use comparison graphs to justify the choice between candidate designs.
- End with a system-level visualization that reconnects the individual models.
- Keep technical diagnostic graphs at a deeper level so they do not interrupt
  the main story.
- Write graph headings and captions as findings, not generic labels.

**Working rule:** Every main graph must answer a question or justify a project
decision.

# Rochester 2025 — Model

[View the model page](https://2025.igem.wiki/rochester/model)

## Note

- State who or what each model informs instead of presenting modelling as an
  isolated activity.
- Connect every model explicitly to wet-lab work, experimental design and the
  software that makes the model usable or reproducible.
- After the result, include a short section explaining how the model changed
  the project.
- Turn uncertain parameters and limitations into specific experiments that can
  test or improve the model.
- End each model with a concise summary that a reader can understand without
  following every equation.
- Keep complete derivations and technical diagnostics at a deeper reading
  level rather than interrupting the main argument.
- Use graphs to select operating conditions, identify useful time points and
  support a concrete recommendation.

**Working pattern:** Model result → wet-lab or experimental action → software
or design implementation → handover to the next part of the project.

# Agreed equation presentation

## Main write-up

- Show only the governing equations needed to understand each model's result.
- Name every quantity in plain language before introducing its symbol.
- Present each equation in this order: meaning in words, equation, symbols and
  units, then why it matters.
- Place the graph or finding produced by an equation directly after it.
- Identify the input received from the previous model and the output passed to
  the next model.

## Expandable technical section

Keep supporting equations, assumptions, derivations, initial and boundary
conditions, numerical methods, parameter sources and model checks available in
an expandable section beneath the main explanation.

## Technical appendix

Place complete equation sets, long derivations, full parameter tables, unit
conversions, implementation details and software links in the technical
appendix.

## Presentation rules

- Render equations as accessible mathematics, not screenshots or images.
- Do not show an equation before explaining its purpose.
- Define symbols and units beside the equation.
- Label parameters as measured, literature-derived or assumed.
- Use one consistent symbol for each quantity across all models.
- Keep equations that do not advance the argument out of the main write-up.

**Working pattern:** Question → assumptions → governing equation → result
graph → project impact → handover.

# Agreed after reviewing the three pages again

## Define success before presenting a model

Before the assumptions and equations, state the model's question, the quantity
used to answer it, what outcome would count as success, and whether that
criterion is measured, sourced or assumed.

**Updated working pattern:** Why it matters → question → success criterion →
assumptions → governing equation → result graph → project impact → handover.

## Give the diagrams careful consideration

The main diagram must explain how gold moves through our biological process.
Heidelberg's comparison between a biological process and a conventional process
is also worth considering. We have not yet decided whether this belongs in the
main diagram or in a separate comparison graphic.

## Label the status of evidence

Clearly distinguish experimental measurements, literature values, derived
parameters, assumptions, model predictions, scenarios and theoretical upper
bounds. The evidence status must be visible before the conclusion that depends
on it.

## Make every model handover explicit

At each handover, state the transferred quantity, its unit, its uncertainty or
evidence status, and the conditions under which the next model can accept it.

## Connect the software at the point where it is discussed

When presenting the software used for a model, include direct access to its
implementation, parameter sources and graph data where appropriate. Do not
leave all software connections to one general link at the end.

## Separate completed impact from future work

Distinguish clearly between what the model already changed, the next experiment
it recommends, and longer-term possibilities. Proposed work must not read as a
completed model-to-wet-lab cycle.
